# RFC 0001: MoroccoAPI Foundation

- Status: Draft
- Intended audience: Founding contributors and public reviewers
- Decision deadline: To be scheduled

## Summary

Create a community-maintained, open-source API that normalizes approved Moroccan public open data into stable, documented JSON contracts.

## Problem

Useful Moroccan public data exists across catalogs, spreadsheets, documents, institutional websites, and isolated community repositories. Developers repeatedly spend time locating files, interpreting columns, cleaning values, handling multilingual names, and tracking source updates.

The ecosystem includes useful specialized datasets and APIs, but there is no widely adopted, general-purpose project that combines strict provenance, documented redistribution rights, consistent schemas, API versioning, automated validation, and transparent community governance.

## Goals

- Provide a stable API for a small number of high-value public datasets.
- Preserve source, license, retrieval date, and transformation history.
- Publish machine-readable adapted databases when required by source licenses.
- Generate OpenAPI documentation from validated schemas.
- Make contributing a new source repeatable and reviewable.
- Support Arabic, French, and English labels when verified.

## Non-goals

- Acting as an official government service.
- Publishing personal data or identity lookups.
- Bypassing authentication, rate limits, paywalls, or website terms.
- Redistributing financial market feeds without explicit permission.
- Maximizing endpoint count before reliability is established.
- Guaranteeing legal or administrative validity of API responses.

## Proposed MVP

### Domain 1: Administrative geography

- Regions.
- Provinces and prefectures.
- Communes.
- Multilingual names and stable internal identifiers.

### Platform capabilities

- `/api/v1` versioning.
- OpenAPI documentation.
- Consistent errors and pagination.
- Per-response provenance metadata.
- Health and source-status endpoints.
- Automated schema and integrity checks.

## Dataset acceptance

A dataset may be integrated only when all of the following are documented:

1. The source and producer are identified.
2. The applicable license or written permission is available.
3. Redistribution and the intended use are permitted.
4. Personal and sensitive data risks have been reviewed.
5. Transformations are reproducible.
6. Update frequency and failure behavior are defined.
7. Attribution requirements can be satisfied.

## Proposed response model

Successful responses contain `data` and `meta`. Collection responses may also include pagination. Errors contain a stable machine-readable code and a human-readable message.

Provenance metadata should include:

- Dataset identifier.
- Producer.
- Source URL.
- Source license.
- Source update date, when known.
- Retrieval date.
- MoroccoAPI transformation version.

## Architecture

The implementation stack is intentionally undecided until the founding contributors review operational cost, contributor familiarity, deployment portability, and maintenance burden.

The initial architecture should prefer:

- A single deployable API rather than microservices.
- Schema-first validation.
- Reproducible extraction and transformation pipelines.
- Versioned static snapshots where practical.
- Minimal infrastructure and no mandatory paid dependency.

## Licensing proposal

- Code: Apache-2.0.
- Adapted ODbL databases: ODbL-1.0.
- Documentation: CC BY 4.0, subject to final approval.
- Individual sources: original license and notices retained.

Code and dataset licenses must not be conflated. A code license does not relicense third-party data.

## Governance proposal

- Public technical and data-source decisions.
- Two approvals for high-impact schema or licensing changes once enough maintainers exist.
- The founding maintainer may break ties during the incubation phase.
- Maintainer status is earned through consistent, constructive contribution.
- Conflicts of interest must be disclosed.

## Risks

- Stale or inaccurate source data.
- Ambiguous source licensing.
- Upstream format changes.
- Inconsistent administrative identifiers.
- Community enthusiasm without long-term maintenance.
- Users treating a community API as legally authoritative.

## Open questions

1. Which authoritative source should define the first administrative hierarchy?
2. Should the first API be implemented with Fastify, NestJS, another framework, or a different language?
3. Where should the public service be hosted?
4. Should documentation be licensed under CC BY 4.0?
5. Who will serve as the first three maintainers?
6. Which public contact channel should the project publish?
